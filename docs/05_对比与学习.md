## 1. 核心定位与架构演进对比

旧参考工程（`Project Iris V3.0`）验证了**“Android 用户空间如何在共享宿主 Linux 内核中启动、渲染图形并实现多开”**；而本项目（**虹膜空间 / IrisBox**）则解决**“普通使用者仅通过安装 APK、授予 Magisk Root 并选择 ROM 文件，如何安全、可重复地部署并维护这套多实例环境”**。

| 维度 | 旧参考工程（Project Iris V3.0） | 本项目（IrisBox / 虹膜空间） | 源码学习入口 |
| :--- | :--- | :--- | :--- |
| **特权入口与部署** | `HostRootEntry` 仅拉起电脑预先部署好的后台 | App 内置宿主预检、签名引擎自动安装与后台重连恢复 | `RootShell`、`EngineInstaller`、`HostRootEntry` |
| **ROM 导入来源** | 依赖固定设备路径下的手工解压镜像 | Android SAF 文档 URI 选择、ZIP 清单与逐文件 SHA-256 校验、独立 ROM 库 | `SetupActivity`、`PackageArchive`、`make_rom.py` |
| **ROM 适配材料** | 混杂在 `runtime` 目录内的固定载荷与 RC | 随 ROM 封装 `compat/` 并由 APK 内置 `rom-profile.json` 双重锁定摘要 | `inner.sh`、`rom/compat/`、`package_engine.py` |
| **实例注册表** | 初始化自带默认实例 `7` / `8` | 初始为空注册表，由用户按需创建（内部 ID 从 `1007` 起分配） | `instances.sh`、`InstanceCatalog` |
| **ROM 版本绑定** | `common.sh` 全局固定单一 ROM 路径 | 每实例通过 `config/rom_v1/ID.id` 独立绑定，导入新 ROM 仅改变后续新建实例默认值 | `common.sh`、`instances.sh` |
| **命名空间与隔离** | 原厂 `init`、六类命名空间、OverlayFS 与 cgroup | 升级为包含 **User Namespace** 的七类命名空间，包名/目录/网卡/资源组全面独立 | `irisbox_userns.c`、`wrapper.sh`、`inner.sh` |
| **显示、输入与文件** | 已验证的 Producer / Gateway / JNI 共享缓冲区管线 | 复用核心图形与文件传输协议，宿主包名与抽象 Socket 完全独立分配 | `display.sh`、`DisplayActivity`、`FileActivity` |
| **网络权限策略** | 宿主全局 BPF 分派器 + 每实例 UID 权限表 | 核验后安全复用共享分派器，仅注册 `1007`–`1134` 私有表，**严禁 `restore` 或抢占** | `network.sh`、`policy.c` |
| **可选 Google 层** | 从匹配的宿主系统中实时抽取静态文件 | 由私有 ROM 携带经校验的 54 项静态文件层，完全不依赖宿主是否安装 Google | `guest_layer.sh`、`rom/compat/google/` |
| **验收标准** | 在已有开发数据的单机上验证功能可用 | 验证从 APK 安装、ROM 导入到双开的完整闭环，同时严格保护旧工程不被破坏 | [实机验收记录](06_验收记录.md)、`tools/device.py` |

## 2. 推荐源码阅读顺序

建议不要直接从庞大的 AOSP 源码树入手，而是沿着**“产品交互层 → 后台管理层 → 容器引导层 → 子系统专项”**自顶向下阅读：

1. **产品安装与导入链路**：`SetupActivity` → `SetupService` → `EngineInstaller` → `PackageArchive`
2. **后台重连与实例生命周期**：`HostRootEntry` → `manager.sh` → `BufferBroker` → `instances.sh` / `ctl.sh` → `wrapper.sh` / `irisbox_userns.c` / `inner.sh`
3. **专项子系统实现**：
   - 网络 BPF 分派与 UID 策略：`engine/native/inet/policy.c`、`engine/runtime/network.sh`
   - 图形缓冲区与输入映射：`app/viewer/native/buffer_viewer.cpp`、`engine/native/buffer/buffer_producer.cpp`、`PointerGeometry.java`
   - 音频回环与宿主播放：`engine/audio/AudioBridge.java`、`engine/runtime/audio.sh`
   - 宿主交换空间控制：`engine/runtime/host_swap.sh`、`HostSwap.java`

> [!TIP]
> **源码精读六问**：阅读任一模块时，建议记录：① 输入来自哪里？② 如何校验调用方与目标会话身份（`PID:start_tick` / `revision`）？③ 代码运行在哪个命名空间与 UID 下？④ 修改了哪项持久或内核资源？⑤ 怎样判定真正完成（而非仅发出请求）？⑥ 发生中断或失败时如何安全回收？

## 3. 动手实验路线（8 项基础实验 + 5 项进阶实验）

### 基础架构实验（8 项）
1. **标注进程执行空间**：为 `SetupActivity`、`RootShell`、`BufferBroker`、`ctl.sh`、`inner.sh` 与 `Guest init` 分别标出其所属的 `App UID`、`Host root` 或 `Guest PID 1`（映射 UID），解释为何 `su` 成功但未加 `--mount-master` 会落入错误的挂载命名空间。
2. **追踪 ROM 导入全生命周期**：从系统文件选择器返回的 `content://` URI 出发，追踪至 `openInputStream`、ZIP 条目校验、SHA-256 比对、root 暂存目录与最终 ROM 注册表，验证错误摘要、`../` 路径穿越和缺失文件均在入库前被拦截。
3. **追踪 ROM 版本绑定**：创建一个实例并记录其绑定的 ROM ID，随后导入另一个不同 ID 的 ROM。验证已有实例的底层 ROM 保持不变，理解为何已有实例的 Overlay `upper` 写层不能盲目直接套用到另一份底层镜像上。
4. **追踪单次实例启动**：依序观察 `instances.sh` 记录 `revision` → `ctl.sh` 创建启动尝试 → `wrapper.sh` 加入 cgroup 并创建命名空间 → `inner.sh` 准备挂载并 `pivot_root` → 原厂 `init` 拉起系统服务，区分“内核进程存在”与“Android 桌面真正就绪”。
5. **验证多实例隔离**：对比两个运行中实例的 `user` / `net` / `mnt` / `pid` 命名空间、私有 `binderfs` 节点及 `upper` / `data` 目录，验证相同包名应用在两个实例内的数据完全独立，且停止其中一个实例绝不影响另一个实例。
6. **区分网络连通与 Socket 创建权限**：理解路由与 NAT 负责数据包转发，而根 cgroup BPF 的 UID 权限表决定应用能否调用 `socket()`。验证为何实例拿到 IP 地址不等于普通无权限应用能联网，以及为何 BPF Map 必须绑定内核 `netns cookie` 而非外层实例编号。
7. **对比低频列表预览与全屏共享缓冲区**：分别阅读列表页 1 fps JPEG 抓图链路与全屏 `Surface` 共享图形缓冲区 + Fence 释放 + 输入坐标变换链路，说明为何管理 HTTP 端口不传输全屏视频流，以及为何修改包名时 JNI 方法签名也必须同步迁移。
8. **演练异常恢复与幂等重连**：测试宿主 App 退出重开、停止 `BufferBroker` 后由 App 自动恢复、故意导入损坏归档包，以及在临时测试实例中执行重置与删除，确认全过程无需通过“重启树莓派宿主”来恢复状态。

### 产品化与实机排障进阶实验（5 项）
9. **音频助手故障注入与自愈（v0.1.1）**：主动终止经身份核验的实例音频采集助手进程，观察 Guest `init` 自动重启采集端、宿主监督脚本自动更换 `AudioTrack` 播放器并恢复非零 PCM 采样，而实例主桌面会话（`PID:start_tick`）保持不变。
10. **跨越 `pivot_root` 的 BusyBox 路径边界（v0.1.2）**：宿主侧脚本使用 `/data/irisbox/host/bin/busybox`，但在 `pivot_root` 进入实例根之后该路径已不可见，必须切换为已复制进实例的 `/system/bin/busybox`。检查所有通过 `ctl.sh exec` 传入实例执行的命令参数，理解“宿主存在的路径不等于实例命名空间内存在”。
11. **纯 AOSP 无可选组件冷启动（v0.1.2）**：存量实例的写层或可选 Google 层可能顺带创建了系统目录，从而掩盖基础镜像的目录缺失。通过启动全新纯 AOSP 实例定位并修复 `product/etc/init` 目录创建逻辑，体会为何验收必须同时覆盖“老数据迁移恢复”与“全新空白数据冷启动”。
12. **真实大型应用暴露的身份隔离深层依赖（v0.1.5）**：
    - **存储项目配额（`vold`）**：追踪 `getExternalFilesDir → StorageManager → vold::PrepareAppDirFromRoot → SetQuotaProjectId → 内核 fileattr_set_prepare`，理解为何映射了 `uid_map` / `gid_map` / `projid_map` 后内核仍拒绝非初始 User Namespace 修改项目配额标志，以及为何只能在严格匹配身份下跳过配额标记而绝不能跳过 `chown`/ACL 检查或退回 Host UID 0（见 [`engine/native/storage/README.md`](../engine/native/storage/README.md)）。
    - **相机框架空设备契约（YouTube ANR）**：理解“禁用物理摄像头”不等于“删除 `cameraserver` 框架服务”。从 YouTube 启动 ANR 的主线程锁追踪到后台线程阻塞在 `Camera.getNumberOfCameras()`，验证恢复原厂框架服务并禁用物理 Provider（正常返回 `0` 台摄像头）才是符合 Android 框架契约的修复方式。
13. **宿主全局交换空间锁继承与游戏输入诊断（v0.1.6）**：
    - **Android `mksh` 文件描述符继承**：宿主 Swap 属于全局资源，必须与实例启动共享互斥锁。Android 的 `mksh` 默认将额外文件描述符设为 `FD_CLOEXEC`，必须实机验证子进程锁继承并在长驻后台进程中显式关闭锁 FD。
    - **区分触控故障与游戏教程规则**：在排查《愤怒的小鸟 2》“拉弓未发射”时，通过抓取保持按住状态下的原生帧画面，观察到弹弓已真实随触控拉动但显示红色叉号提示，对齐绿色教程轨迹后即可正常发射——学会结合输入事件、原生帧、会话状态与 OOM 计数科学排障，而非凭主观猜测归咎于内存或输入通道损坏。

# 从旧 V3.0 到 App 产品：对比与学习

## 先理解变化的边界

旧项目已解决“Android用户空间怎样在共享宿主内核中运行、显示和多开”。本项目解决“用户只安装App、授权、导入文件后怎样重复建立同一环境”。核心引擎保留，部署、输入可信边界、版本和设备资源归属需要重新设计。

| 主题 | 旧项目 | 本项目 | 学习入口 |
|---|---|---|---|
| 正常root入口 | HostRootEntry拉起已部署后台 | 首次检查、内置引擎安装、之后恢复后台 | RootShell、EngineInstaller、HostRootEntry |
| ROM来源 | 固定设备路径中的镜像 | SAF文档URI、ZIP清单、逐文件校验、独立库 | SetupActivity、PackageArchive、make_rom.py |
| ROM适配 | runtime内固定载荷/RC | ROM中的compat及APK兼容profile | inner.sh、rom/compat、package_engine.py |
| 实例创建 | 初始化默认7/8再新增 | 空注册表，用户创建1007起实例 | instances.sh、InstanceCatalog |
| 镜像版本 | common.sh固定一个ROM | 每实例ROM记录，导入只改变新实例默认 | common.sh、config/rom_v1 |
| 多开 | 原厂init、六空间、Overlay和资源组 | 沿用核心，目录/资源名独立 | wrapper、inner、prepare_groups |
| 显示/键鼠/文件 | producer/gateway/JNI等已验证 | 配套协议复用，宿主包名/socket另分配 | display.sh、DisplayActivity、FileActivity |
| 联网 | 宿主全局分派器+每Guest权限表 | 验证共享分派器，新增独立cookie映射，禁止restore | network.sh、policy.c |
| Google | 从匹配宿主抽取固定文件 | ROM自带静态层，不依赖宿主Google安装 | guest_layer.sh、compat/google |
| 验收 | 开发设备已有数据上的功能结果 | 新建环境完整安装/导入/启动，还需保护旧环境 | 验收记录、device.py |

## 建议八次学习实验

1. **画清执行位置。** 给SetupActivity、RootShell、Broker、ctl、inner、Guest init分别标注App UID/Host root/Guest PID1。验收：解释为什么su成功仍可能处于错误mount namespace。
2. **追踪一个文件。** 从系统选择器返回content URI，追到openInputStream、ZIP条目、摘要、root暂存和最终ROM。验收：坏SHA、`../`和缺文件都不能登记。
3. **追踪一个版本。** 新增实例时记录ROM ID，再导入另一个ID。验收：旧实例的ROM文件不变，原写层不能无条件套到另一个ROM上。
4. **追踪一次启动。** instances记录revision；ctl创建attempt；wrapper加入cgroup和unshare；inner挂载并pivot；init接管服务。验收：区分“进程在”和“桌面就绪”。
5. **解释多开。** 对比两个实例的net/mnt/pid namespace、Binder设备和upper/data目录。验收：两边账号和文件独立，停止一个不会结束另一个。
6. **解释网络权限。** 路由/NAT保证数据通路，UID权限表控制应用能否创建socket。验收：有IP不等于普通应用联网；理解cookie、map ID为何不能用实例号替代。
7. **解释图形。** 先读列表JPEG预览，再读全屏共享buffer/fence/RELEASE和输入坐标。验收：说明为何管理HTTP不承载全屏视频，为什么Native JNI包名也必须迁移。
8. **练习恢复。** App退出重开、后台停止重启、导入错误文件、在新测试实例中重置/删除。验收：保持旧工程hash、旧活跃进程tick、宿主boot_id不变，不用重启宿主“修好”。

## 推荐阅读顺序

先读本项目使用说明和技术架构，再沿`SetupActivity → SetupService → EngineInstaller → PackageArchive`阅读产品流程。随后看`HostRootEntry → manager.sh → BufferBroker → instances/ctl → wrapper/inner`。最后研究联网policy和图形JNI；不要从整个AOSP代码树开始。

每次记录：输入是什么、怎样验证身份、在哪个空间执行、改变哪个资源、如何确认成功、失败怎样回收。把历史验收、源码逻辑和新设备实测分别记录。旧项目双账号/游戏验收可以说明复用能力来源，不能自动证明新导入环境已通过同样验收。

旧工程入口：`PATH_TO_PREVIOUS_IRIS_PROJECT\README.md`；原学习技能树和各阶段失败记录仍在旧工程docs内，本项目不复制整个课程或历史日志。

## 登录后回归带来的学习点

本项目增加了独立音频桥、视频解封装服务恢复、启动健康处理及单帧preview退出修复。对应源码为`engine/audio/AudioBridge.java`、`engine/runtime/audio*`和`engine/native/buffer/buffer_producer.cpp`。这些改动只在新目录和新实例生效，旧项目保留原始状态。

可以追加三项实验：杀死经身份核验的Guest音频助手，观察init重启助手、Host播放器重新建立且Guest主session不变；用普通UID编码/播放MP4，区分编码器、mediaextractor和播放器；连续读取JPEG预览并检查独立序列及崩溃缓冲区，区分画面更新与辅助进程健康。登录后的原始证据保持私有，报告只记录账号数量与不可逆对照结果。

## 产品化新增的两项实验

**追踪同一个 BusyBox 路径的边界。** 宿主侧使用 APK 安装到 `/data/irisbox/host/bin/busybox` 的校验载荷；切根后这个路径已不可见，必须使用复制进实例的 `/system/bin/busybox`。不仅要检查 pivot_root 后的脚本，还要检查 Host 调用 `ctl exec` 时传入的 Guest 命令参数。路径存在于开发宿主不能证明它存在于新用户设备或 Guest 命名空间。

**用真正不带可选组件的 ROM 首次启动。** 旧实例的写层和 Google 层可能替引擎创建了目录，掩盖默认系统的缺项。本轮纯 AOSP 新实例暴露了 `product/etc/init` 缺失，修复为引擎在已核验的私有写层创建核心所需目录，不再依赖 Google。验收应同时包含老数据恢复和新空白数据启动。

## 0.1.3：追随旧项目补齐身份隔离

旧项目2026-10-20已完成User namespace整合；本次提取时的e13属于更早检查点，不能继续把它当成旧项目最新能力。移植必须成套处理属主/ACL/capability、Overlay metacopy、受委派cgroup、网络表身份、显示FD交接、Magisk挂载及闹钟兼容。虹膜空间另有0700私有根和PCM桥，不能照抄旧路径或只加CLONE_NEWUSER。实现与迁移说明见09；旧工程只读，UID范围和持久数据完全分开。

## 0.1.5：用真实应用发现身份隔离的配套缺口

User namespace不是只补uid_map/gid_map。项目ID也有独立映射；而匹配内核仍禁止容器改变项目配额状态。沿`ProbeActivity.getExternalFilesDir → StorageManager → vold.PrepareAppDirFromRoot → SetQuotaProjectId → 内核fileattr_set_prepare`追踪，能解释为何App有普通UID权限却拿不到目录。最终适配仅处理不支持的项目配额设置，不能忽略chown、ACL或权限失败，更不能让vold回到Host UID0。用普通App首次创建目录并写入/读回，比“映射表存在”更能证明可用，见`engine/native/storage/README.md`。

同样，停用物理摄像头不等于可以删除整个相机框架服务。YouTube启动时查询设备数，缺服务会等到ANR；保留框架、禁用物理provider并返回0台设备才能表达不支持。学习时从ANR主线程锁追到后台线程的Camera.getNumberOfCameras，再验证服务返回，避免用增加超时或修改应用掩盖系统缺项。

命名迁移则是数据/权限迁移问题：新包拥有新UID，需要正常重新授权；旧授权只在独有UID和归属核验后撤销。后台绝对路径、显示指针、音频RC、JNI类名和已生成二进制都要检查，不能只替换README中的品牌。完整停机快照与事务回退属于迁移本身，而非事后补救。

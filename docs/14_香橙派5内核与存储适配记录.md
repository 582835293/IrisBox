# 香橙派 5（RK3588S / Android 12）内核与外置存储适配记录

本文档记录 IrisBox v2 阶段 2 起步期间（2026-11-16）针对 **16GB Orange Pi 5（Android 12）** 进行宿主内核补全、串口调试定位、驱动兼容及外置 128GB USB SSD 准备的真实过程、补丁设计与避坑经验。

## 1. 宿主硬件与原厂基线采集

通过只读排查获取香橙派 5 原厂系统基线：

| 项目 | 实测值 |
|---|---|
| 设备标识 | `ro.product.device=rk3588s_s`、`ro.product.model=orangepi5`、`ro.hardware=rk30board`、`ro.board.platform=rk3588` |
| 系统与 ABI | Android 12（SDK `32`）、`arm64-v8a`、SELinux `Permissive` |
| 构建指纹 | `rockchip/rk3588s_s/rk3588s_s:12/SQ3A.220705.003.A1/eng.orangepi.20261029:userdebug/release-keys` |
| 内存与交换 | 物理内存 `16070332 kB`（约 15.3 GiB）+ `zram0`（`8035164` KiB） |
| 引导与分区 | TF 卡 `mmcblk0`（14.6 GiB），`userdata` 仅约 10 GiB；`boot -> /dev/block/mmcblk0p7`（Boot Image Header v2，`page_size=2048`，`header_size=1660`，含 `kernel`、`ramdisk` gzip、`second` `RSCE`、`dtb` `692141` 字节）；`vbmeta` flags `0x02`（校验关闭，`verifiedbootstate=orange`） |
| 内置 Root | 原厂自带 `/system/xbin/su`（Toybox su，支持 `/system/xbin/su 0 /system/bin/sh -c`），**未安装宿主 Magisk**（`/data/adb` 为空） |
| GPU 节点与 HAL | `/dev/mali0`（`0666`）、`/dev/dma_heap/*`、`/dev/dri/renderD128`；`android.hardware.graphics.allocator@4.0-impl-bifrost.so` / `mapper@4.0-impl-bifrost.so`、`libGLES_mali.so`（`g18p0-01eac0-2`）、`vulkan.rk3588.so` |
| BPF 形态探针 | `/sys/fs/cgroup` 上 `BPF_PROG_QUERY(BPF_CGROUP_INET_SOCK_CREATE)` 返回 `prog_cnt=1`、`attach_flags=0x0`、`id=27`；`/sys/fs/bpf/prog_netd_cgroupsock_inet_create`（`id=27`）与 `/sys/fs/bpf/map_netd_uid_permission_map`（`HASH, key=4, val=1, max=2000`），与 Android 13 单程序替换模型一致 |

原厂 `/proc/config.gz` 与 `/proc/self/ns/` 核对发现以下硬缺口：
- 缺少 `CONFIG_USER_NS`、`CONFIG_PID_NS`、`CONFIG_IPC_NS`（被 `depends on (SYSVIPC || POSIX_MQUEUE)` 隐藏）、`CONFIG_CGROUP_PIDS`；
- 内核 `5.10.160` 已内置 `net->net_cookie` 与 `BPF_FUNC_get_netns_cookie`（helper #122），但未提供用户态 `getsockopt(SOL_SOCKET, SO_NETNS_COOKIE=71)` 接口。

## 2. 内核编译基线与关键避坑

1. **源码分支精确匹配**：
   - `orangepi-xunlong/linux-orangepi` 中 `orange-pi-5.10-rk3588` 为 `5.10.110`，而 **`orange-pi-5.10-rk35xx`** 才是 **`5.10.160`**，与实机一致；
   - 必须传 `CROSS_COMPILE=aarch64-linux-gnu-` 配合 `LLVM=1 LLVM_IAS=1`（使用 `clang-r450784d` Clang 14.0.6），否则 `olddefconfig` 会误判主机架构导致 `CONFIG_SHADOW_CALL_STACK` 等 ARM64 安全特性被关闭；
   - 源码树内 Realtek 无线驱动 `Makefile` 使用 `EXTRA_CFLAGS += -I$(src)/include`，不支持 `O=` 独立输出目录编译，需直接在内核树内（in-tree）编译；同时创建空 `.scmversion` 文件消除 `KERNELRELEASE` 末尾 `+` 号，保持 `5.10.160` 精确版本；关闭 `CONFIG_DEBUG_INFO` 控制构建体量。
2. **OverlayFS `metacopy` 确认**：
   - 查看 `fs/overlayfs/super.c` 确认 `CONFIG_OVERLAY_FS_METACOPY` 仅控制模块参数 `ovl_metacopy_def` 默认值，`mount -t overlay -o metacopy=on` 本身无需开启该宏即可使用；保持 `# CONFIG_OVERLAY_FS_METACOPY is not set` 既支持运行时 `metacopy=on`，又满足 [preflight.sh](../app/viewer/assets/preflight.sh#L49-L50) 对 `/sys/module/overlay/parameters/metacopy == N` 的检查。
3. **`MODVERSIONS` ABI 变化与网卡驱动内置**：
   - 原厂启用 `CONFIG_MODVERSIONS=y`，开机加载 `/vendor_dlkm/lib/modules/` 中的 `8821cu.ko`（`wlan0`）、`r8168.ko`、`yt6801.ko`、`rtk_btusb.ko`（原厂依赖 `module_layout` CRC `0x55a12ad9`）。
   - 开启 `USER_NS`、`PID_NS`、`IPC_NS`、`CGROUP_PIDS` 后，新编 `vmlinux.symvers` 中 `module_layout` CRC 变为 `0xdba2b9d3`（`usb_submit_urb` 等亦变化），若继续依赖 `/vendor_dlkm` 原厂 `.ko` 会导致网卡模块拒绝加载并失联。
   - **解法**：将 4 个实机活跃驱动（`CONFIG_RTL8821CU=y`、`CONFIG_R8168=y`、`CONFIG_FUXI=y`、`CONFIG_BT_HCIBTUSB_RTLBTUSB=y`）全部直接内置编译进 `Image`，并修复 `drivers/net/wireless/rtl8811cu/include/ieee80211.h` 中 3 处 `extern __inline`（在 Clang 14 `-O1` 下会产生未定义引用）为 `static inline`。
4. **3 项必须的内核源码补丁**（补丁归档于本地 `validation/private/opi5_backup/irisbox_opi5_5.10.160.patch`）：
   - **补丁 1（`SO_NETNS_COOKIE = 71`）**：在 `include/uapi/asm-generic/socket.h` 定义 `#define SO_NETNS_COOKIE 71`，在 `net/core/sock.c` `sock_getsockopt()` 中调用内核既有 `__net_gen_cookie(sock_net(sk))`，与 BPF helper #122 同源一致。
   - **补丁 2（兼容旧版 DTB 的 `dw-hdmi-qp` 防空指针崩溃）**：初版刷机后通过 3-pin 串口（波特率 **`1500000`**）抓包定位到 `dw_hdmi_qp_bind+0x6b0` 空指针崩溃（`x25 = -22 / -EINVAL`）。原因是新内核 `dw-hdmi-qp.c` 在 `CONFIG_HDCP14` 分支无条件取第 2 段 `IORESOURCE_MEM`（`0xfde90000`），而原厂 Android 12 `dtb` 仅提供第 1 段 `reg`，返回 `-EINVAL` 后又跳转至 `err_ddc` 去调用尚未初始化的 `hdmi->connector.funcs->destroy`（偏移 `0x40` 空指针）。修复方式：无第 2 段内存资源时跳过 HDCP14 注册，并在清理路径增加 `hdmi->connector.funcs` / `encoder->funcs` 空指针守卫。
   - **补丁 3（补充 `/vendor/etc/firmware` 搜索路径）**：首轮进入系统后发现卡在 `bootanim`，`dmesg` 显示 `Direct firmware load for mali_csffw.bin failed with error -2`。原厂 cmdline 传入 `firmware_class.path=/system/vendor/firmware`（实际仅含 4 个相机 `.rkl` 文件），而 `mali_csffw.bin` 与无线/蓝牙固件位于 `/vendor/etc/firmware/`。通过 `COM7` 向 `/sys/module/firmware_class/parameters/path` 热写入 `/vendor/etc/firmware` 后，Mali GPU 固件与桌面、Wi-Fi 立即恢复；随后将该路径固化进 `drivers/base/firmware_loader/main.c` 的 `fw_path[]` 回落列表。

## 3. 刷机校验与实机内核能力验收（2026-11-16）

最终镜像 `opi5_irisbox_boot.img`（`44,302,336` 字节，保留原厂 `ramdisk`、`second` `RSCE` 与 `dtb`，SHA-256 `ed9412a1bc3e90e9ba72cbe8500b76f574bd801cfa08e24df8fb239aa7818012`）写入 `/dev/block/by-name/boot` 并回读校验一致后，重启全自动进入系统并通过以下核验：

- **自动启动与联网**：`sys.boot_completed=1`、`init.svc.bootanim=stopped`、`Permissive`；`dmesg` 在 `[18.191637]` 自动完成 `Loading Mali firmware 0x1010000`；`wlan0 UP DEVICE_IP/24`。
- **7 层 Namespace**：`/proc/self/ns/` 具备 `cgroup`、`ipc`、`mnt`、`net`、`pid`、`user`、`uts`；使用已核验 `busybox` 实测 `unshare -m -p -n -u -i -f --propagation private /system/bin/true` 与 `unshare -U /system/bin/true` 均返回成功。
- **`SO_NETNS_COOKIE`**：静态编译的 `netns_cookie_probe` 实测 `host_netns_cookie=1`，进入新 `CLONE_NEWNET` 后 `guest_netns_cookie=4097`（`distinct=1`）。
- **Cgroup 与 Overlay**：`/sys/fs/cgroup/cgroup.controllers` 为 `pids`，`/dev/memcg/memory.limit_in_bytes`、`/dev/cpuctl/cgroup.procs`、`/dev/cpuset/cgroup.procs`、`/dev/blkio/cgroup.procs` 全数存在；`/sys/module/overlay/parameters/{index,metacopy,xino_auto,redirect_dir,nfs_export}` 全为 `N`。
- **关键设备节点**：`/dev/mali0`、`/dev/binderfs/binder`、`/dev/dri/renderD128`、`/dev/dma_heap/system` 均正常创建。

## 4. 外置 128GB USB SSD、宿主 Magisk 与 `opi5-a12-v1` 适配验收（阶段 2 完成）

- **外置 SSD 分区与防抢占**：外置 USB 3.0 SSD（`/dev/block/sda1`，`30452992` 个 4k 块，约 116 GiB）从 Android `vold` 卸载 exFAT 后格式化为 `ext4`（`LABEL="irisbox_ssd"`、`UUID="17513715-74ee-4a53-9cb9-568e3524c61f"`），`e2fsck -fy` 通过；`vold` 自动维持其 `unmounted` 状态，不与 `/data/irisbox` 抢占挂载。
- **宿主 Magisk v30.7 部署与环境完整化经验**：
  - 使用官方 `Magisk-v30.7.apk`（SHA-256 `e0d32d2123532860f97123d927b1bb86c4e08e6fd8a48bfc6b5bee0afae9ebd5`，与 `adaptation.json` 校验一致）在设备端执行官方 `boot_patch.sh`（`KEEPVERITY=true`、`KEEPFORCEENCRYPT=true`、`PREINITDEVICE=cache`），生成 `opi5_irisbox_magisk_boot.img`（`44,312,576` 字节，SHA-256 `c3621212d5a0f1a2463b7aae17596bd0b37348a7fb083152fc98d297b122cf41`）写入 `boot` 分区并回读校验通过。
  - **关键排障**：若仅离线刷入修补后的 `boot.img` 而未将 APK 内二进制与脚本释放到 `/data/adb/magisk/`，`post-fs-data` 阶段 `magiskd` 会在 `/cache/magisk.log` 报错 `* Magisk environment incomplete, abort` 并直接跳过 `service.d` 执行，同时 Magisk App 显示 `当前: 无法获取`、`超级用户` 变灰且授权规则无法持久化写入 `magisk.db`。按官方 `updater-script` 规范补齐 `/data/adb/magisk/`（`lib/arm64-v8a/*`、`magisk32`、`assets/*`，`chmod 755`、`chown 0:0`、`env_check 30.7 30700` 返回 `0`）并重启后，Magisk App 正常识别 `30.7 (30700)`，永久授权与 `service.d` 全部恢复。
- **外置 SSD 挂载、写前拦截与开机恢复实现**：
  - `engine/boards/opi5-a12-v1/board.json` 开启 `requireExternalMount: true`、`verified: true`、`bpfMode: "a12-legacy-single"`，同步工具 [board_profiles.py](../tools/board_profiles.py) 支持导出 `BOARD_REQUIRE_EXTERNAL_MOUNT` 与 `IRIS_REQ_EXT_MOUNT`。
  - [storage_ssd.sh](../app/viewer/assets/storage_ssd.sh) 仅依赖 Android `/system/bin/*`（无 BusyBox 前置依赖），实现候选盘扫描、UUID 绑定（`/data/adb/irisbox_storage.conf`，`0600`）、盘内标识核验（`/data/irisbox/.irisbox_ssd_marker`，`0600`）、安全卸载、以及 Magisk `service.d` 开机恢复脚本（`/data/adb/service.d/irisbox-storage.sh`，`0700`，带 `# IRISBOX_MANAGED_STORAGE_V1`）。
  - [HostStorage.java](../app/viewer/src/com/iris/viewer/buffer/HostStorage.java)、[HostTools.java](../app/viewer/src/com/iris/viewer/buffer/HostTools.java)、[preflight.sh](../app/viewer/assets/preflight.sh) 与 [common.sh](../engine/runtime/common.sh) 在任何写入/检查/启动前强制校验 `/data/irisbox` 为独立 `ext4` 块设备且标记一致，未挂载时拦截并提示，不向内部 TF 卡落盘。

## 5. 阶段 2 真机联调发现与修复的 3 项关键问题

1. **`board.sh` 在 Android `mksh` 下因未引号转义 `|` 陷入 99% CPU 死循环**：
   - [board.sh](../engine/runtime/board.sh) 原 `iris_value_in_pipe_list()` 在 `while` 中使用 `${_rest%%|*}` 与 `${_rest#|*}`。RPi4 单设备名 `rpi4` 不含 `|` 未触发该分支；在 OPi5 多别名 `rk3588s_s|orangepi5|rk3588_s|rk3588` 上，Android `/system/bin/sh`（`mksh`）把未转义 `|` 解析为模式分支导致 `_rest` 永不缩减，造成 `instances.sh init` 卡死 99% CPU。
   - **修复**：改为零循环 `case "|$_haystack|" in *"|$_needle|"*) return 0 ;; esac` 并拒绝含 `|` 的 `_needle`，在实机 `mksh` 验证对 `*`/`?`/`|` 均按字面量精确匹配。
2. **Toybox `nsenter` 误解析 `/system/bin/sh -s` 选项**：
   - Toybox 0.8.4 `nsenter` 在没有 `--` 时会把后续命令参数 `-s` 当成自身无效选项（实测报错 `nsenter: Unknown option 's'`）。
   - **修复**：改用 `export IRISBOX_SSD_UUID="$UUID"` 后执行 `exec /system/bin/nsenter -t 1 -m /system/bin/sh <<'IRISBOX_MOUNT_INNER'`，在开机 `service.d` 中稳定进入 PID 1 挂载命名空间完成 `e2fsck -p` 与挂载。
3. **受管开机脚本升级兼容**：
   - 完善 `storage_ssd.sh:hook_check()`，对第 2 行为 `# IRISBOX_MANAGED_STORAGE_V1` 且权限为 `0:0:700:1` 的旧版脚本返回 `1`（标记待更新），仅对非受管第三方文件报错 `FOREIGN_BOOT_HOOK`，避免后续更新 APK 时被自身旧版本脚本拦截。

## 6. 阶段 2 实机终检结果与当前边界

- **未挂载写拦截**：未挂载及执行“安全卸载”后，点击 `1 · 授权与检查` 与 `4 · 管理实例` 均被准确拦截（`外置 SSD 未挂载至 /data/irisbox，已拦截写入内部存储`），`/data/irisbox` 保持空目录不写 TF 卡。
- **`preflight` 与引擎安装**：通过 UI 挂载并启用恢复后，`/data`（dev `64775`）与 `/data/irisbox`（dev `2049`）隔离正常；`preflight` 全绿识别 `支持配置：香橙派5 / ARM64 / opi5-a12-v1`；内置引擎 `0.2.1-e29`（58 个文件）安装至 SSD 且 `sha256sum -c files.sha256` 全数通过；`iris_inet_policy inspect` 返回 `attached=27 host_map=36 type=1 key=4 value=1 max=2000 flags=0 cookie=1`。
- **重启自动挂载恢复**：清空旧日志执行 `adb reboot` 后，`/data/adb/irisbox-storage.log` 记录 `irisbox_ssd: clean, 107/7618560 files, 615238/30452992 blocks` 与 `mounted /dev/block/sda1 -> /data/irisbox (17513715-74ee-4a53-9cb9-568e3524c61f)`，`SetupActivity` 首页直接回显 `引擎：0.2.1-e29`。
- **运维备注与阶段 3/4 待办**：
  1. 若设备同时记忆多个 Wi-Fi 或刚冷启动未激活 TCP ADB，可通过 3-pin 串口 `COM7`（`1500000` 波特率）检查 `wlan0` 与按需拉起 `adbd`；
  2. 阶段 3 Guest ROM 构建（`rom/profiles/opi5-a12-v1/compat` 与 Mali-G610 Gralloc/HWC 渲染）及阶段 4 目标应用测试尚未开始。

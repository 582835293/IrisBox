# 网络上行探测与出口策略设计

本文档针对当前 IrisBox 在切换宿主物理网络、宿主机开启 VPN/代理软件时容器网络适配不足的问题，结合现有 [board.sh](../engine/runtime/board.sh)、[network.sh](../engine/runtime/network.sh) 及树莓派 4 宿主（Android 13）实际内核策略路由实现，给出“上行动态探测 + APK 出口策略控制”的详细设计与改造边界（已按用户 2026-11-13 评审结论定稿）。

---

## 一、现状与痛点定位

基于当前代码与树莓派 4 实机抓包/路由核查，现有网络模型存在以下三处结构性限制：

1. **启动期一次性静态选网，运行期不跟随切换**
   - [board.sh](../engine/runtime/board.sh#L154-L166) 中的 `iris_select_uplink` 仅在实例启动准备（`network.sh prepare`）时按 `BOARD_UPLINK_CANDIDATES`（如树莓派 profile 中配置的 `wlan0`，或默认 `wlan0 eth0`）顺序检查哪个接口对应的独立路由表存在 `^default `。
   - 一旦选定上行网卡 `UPLINK`，即写入 `$STATE/uplink` 并固定配置 `ip rule pref 12009 iif rv<ID>h lookup <UPLINK>`、双向 `FORWARD` 规则及 `POSTROUTING -o <UPLINK> -j MASQUERADE`。
   - **后果**：实例运行中宿主切换 Wi-Fi / 有线网（`eth0`）/ USB 共享网卡，或板卡仅配了 `wlan0` 但用户实际插入有线网线时，容器无法自动发现活动出口或热切换，必须停机重启且受限于静态候选列表。

2. **宿主开启 VPN（`tun0`）时，容器流量默认绕过 VPN**
   - 实机验证（开启 FlClash VPN 后检查宿主路由）：Android `VpnService` 创建的 `tun0` 路由表并不包含 `default` 路由条目，而是包含覆盖公网 IPv4 空间的 CIDR 分片路由（如 `1.0.0.0/8`、`2.0.0.0/7`、……、`255.255.255.254` dev `tun0`），因此 `grep '^default '` 永远不会选中 `tun0`。
   - 同时，宿主既有 `12009: from all iif rv<ID>h lookup wlan0` 优先级高于 Android 自身的 VPN 规则（`16000` / `24000`），且 `16000/24000` 规则主要匹配 `iif lo` 或带 `fwmark` 的本机应用 UID。容器流量直接被强送往物理网卡 `wlan0`，对宿主 VPN 无感。

3. **缺乏 APK 控制面与统一出口抽象**
   - 当前 Viewer APK 与 `BufferBroker` 仅负责开关容器、调整内存/分辨率/Swap，没有任何网络出口配置或当前链路诊断显示。用户需要代理科学上网时，只能手动在宿主开启代理的“允许局域网连接”并在容器内通过命令行写入 `settings put global http_proxy <网关>:<端口>`，既不直观，也无法感知和兜底宿主代理开关或非 HTTP 协议直连。

## 二、设计原则与不可违背的安全红线

1. **与共享 eBPF 权限控制完全正交**：不修改 [policy.c](../engine/native/inet/policy.c) 对无 `INTERNET` 权限应用的拒绝语义，不改变共享 BPF 分派器复用规则与旧 Project Iris 保留表保护逻辑。
2. **精确账本与按所有者原子回收**：所有新增/热更新的 `ip rule`、`iptables` 规则及接口状态必须先记入该实例私有 `$STATE`（如记录当前生效的出口接口、模式、规则选择器），由 `PID:start_tick` 校验归属，停止/崩溃/切换时按原记录精确逐条删除，严禁 `flush` 全局规则或误删其他实例/宿主原有规则。
3. **Host 与 Guest 隔离边界不变**：不向 Guest 注入宿主敏感密钥或代理节点信息；宿主仅对外（按策略）提供网关代理参数或基于 `rv<ID>h` 的宿主内核转发/路由调度。
4. **跨板卡兼容**：不再要求每块板卡在 `board.json` 中穷举所有可能外接网卡名；`board.json` 中的 `uplinks` 退化为“优先顺序/排除过滤提示”，支持按宿主机实时路由动态识别。

## 三、总体架构：两层正交设计

将现有单一的 `iris_select_uplink` 拆解为 **L1（物理上行动态探测与热切换）** 与 **L2（实例出口策略）** 两层：

```
Guest (eth0: 172.30.<N>.2)
   │
   ▼
Host veth (rv<ID>h, gw: 172.30.<N>.1)
   │
   ├──[10909: to 172.30.<N>.0/24 lookup main] (回包回容器)
   │
   ├──[L2 出口策略路由 / 代理通道]
   │      ├── 模式 A：follow_host_uplink  ──► 直接查询 L1 当前最佳物理接口
   │      ├── 模式 B：fixed_uplink        ──► 锁定用户指定的物理接口（如 eth0 / wlan0）
   │      ├── 模式 C：host_vpn_tun        ──► 优先查询 tun0 (公网)，私有/未命中回退 L1 物理接口
   │      └── 模式 D：host_proxy          ──► 物理出站走 L1 + 容器配置/校验网关代理端口
   │
   ▼
[L1 物理出口探测器] <── 动态跟踪宿主当前活跃物理出口 (wlan0 / eth0 / usb0 / ...)
```

## 四、L1 详细设计：宿主物理上行动态探测与热切换

### 4.1 活动物理出口探测算法（替代硬编码候选列表）

探测函数 `iris_probe_active_uplink` 按以下优先级确定当前最佳宿主物理上行接口（自动忽略 `lo`、`dummy*`、`rv*`、`tun*`、`veth*`、`rmnet_r_*` 等虚拟/容器接口）：

1. **优先读取宿主系统选定的默认网络接口**：
   - 通过 Android 宿主系统状态（如 `dumpsys connectivity` 当前活跃 `NET_CAPABILITY_INTERNET` + `NOT_VPN` 默认网络的 `InterfaceName`，或通过 `ip -4 route get 223.5.5.5` / `1.1.1.1` 在非 `tun` 表下的解析设备，配合 `ip rule` 中当前高优先级 `fwmark` 默认网卡表），精确获知 Android 系统当前真正启用的默认物理出口（例如网线插入且 Wi-Fi 断开时会自动指向 `eth0`）。
2. **次级回退扫描所有已 UP 物理接口**：
   - 若系统默认网络查询未命中，遍历 `/sys/class/net/*`（排除 `lo`/`dummy*`/`rv*`/`tun*`/`bridge*` 等内部接口），优先按 `board.json` 中 `host.uplinks` 偏好顺序检查，再扫描剩余 `operstate=up`（或 `LOWER_UP`）且对应 Android 分表 `ip route show table <iface>` 存在 `^default ` 的接口。
3. **无网状态宽容机制（已定稿）**：
   - 允许宿主当前没有任何默认物理路由时以 `uplink=none` 占位状态启动实例（不再因 `exit 4` 拒绝开机）：照常创建 `rv<ID>h`/`eth0`、分配 Guest IP 及回包规则 `PREF_RETURN` 与共享 BPF 权限管控，但暂不写入物理出口 `PREF_OUT`/`FORWARD`/`MASQUERADE`；待宿主恢复联网后由 `reconcile` 热切换自动补齐并记录到账本。

### 4.2 运行期热切换机制（Reconcile）

由现有实例守护/控制面（`watchdog.sh` 轻量周期探测，或 `BufferBroker` 监听宿主 Android `ConnectivityManager.NetworkCallback` 后触发 `network.sh reconcile <ID> <SESSION> <LOG>`）执行：

1. **锁与身份校验**：取得 `$RUN/network.lock`，验证 `owner == $SESSION` 且未清理。
2. **幂等对比**：将当前探测到的物理接口（及当前 VPN `tun0` 在线状态）与 `$STATE/active_egress` 对比；若完全一致，零操作直接退出。
3. **先增后删（或账本化原子替换）**：
   - 若新物理接口 `$NEW_UPLINK` 与 `$OLD_UPLINK` 不同：
     1. 先添加新接口的 `FORWARD`（`_OUT`、`_RETURN`）和 `POSTROUTING MASQUERADE` 规则；
     2. 再切替换 `PREF_OUT`（`12009`）规则指向新表；
     3. 精确删除旧接口 `$OLD_UPLINK` 对应的 `ip rule` 与 `iptables` 规则；
     4. 原子更新 `$STATE/uplink` 与 `$STATE/active_egress`（全过程失败保留旧/新痕迹于账本供 `cleanup_owned` 兜底清除）。

## 五、L2 详细设计：容器出口策略与宿主 VPN / 代理协同

每个实例支持独立配置（并可设全局默认），持久化至 `/data/irisbox/runtime/config/network_v1/<ID>.json`（或 `.conf`），包含 `mode`、`fixedIface`、`proxyPort`、`vpnFallback`（VPN 断开时“回落物理网卡（默认 `fallback_physical`）”或“阻断公网防泄露 `fail_closed`”）。

**常见出口优先级约定（已定稿）**：
- 默认策略按常规系统直连/代理优先逻辑：
  - 未显式开启代理跟随时，默认使用 `follow_host_uplink`（物理活跃网卡优先级：`宿主默认网络接口` > `board.json host.uplinks 偏好顺序` > `其余已 UP 物理网卡` > `none` 占位待命）。
  - 在开启宿主代理协同或自动选路时，按 **宿主透明 VPN（`tun0`） > 宿主局域网 HTTP 代理（`host_proxy`） > 物理直连网卡（`L1`）** 的常见优先级依次判定（待 Phase 2 实测确认 `tun0` 对容器的兼容性细节后再固化自动透明路由默认行为）。
  - `host_vpn_tun` 模式下 `vpnFallback` 默认为 `fallback_physical`（宿主 VPN 关闭时无缝回落当前物理网卡不断网），用户可在 UI 中改为 `fail_closed` 防泄露。

### 模式 1：`follow_host_uplink`（默认：自动物理出口）
- 行为：完全由 L1 自动跟踪宿主活跃物理网卡并热切换，不经过宿主 `tun0`。
- 适用：常规国内网络、本地局域网开发测试、不需要宿主代理的实例。

### 模式 2：`fixed_uplink`（锁定指定物理网卡）
- 行为：强制绑定宿主 `eth0` 或 `wlan0` 等指定接口；适用于双网卡宿主（例如无线做宿主管理、有线专供某容器实例）。若指定接口未就绪则状态标红提示，不自动漂移到其他网卡。

### 模式 3：`host_vpn_tun`（透明跟随宿主 `VpnService` / `tun0`）
针对宿主开启 FlClash / Clash / V2Ray 等 VPN 客户端时，容器免配客户端应用内代理的透明路由模式：
- **前置探测**：检查宿主存在活跃 `tun0`（接口 `UP` 且 `ip route show table tun0` 非空）。
- **核心路由与 NAT 规则**：
  1. 在 `$PREF_OUT`（例如 `12009`）加规则：`iif rv<ID>h lookup tun0`；
  2. 在更低优先级（`$PREF_OUT + 1`，例如 `12010`）加回退规则：`iif rv<ID>h lookup <ACTIVE_PHYS_UPLINK>`（因为 `table tun0` 仅包含公网分片网段，不包含局域网网关 `192.168.x.x` 等私有路由，需回退物理表或 `main`）；
  3. 对跨接口转发放行并做源地址伪装：
     - `FORWARD`: `-i rv<ID>h -s <GUEST_IP>/32 -o tun0 -j ACCEPT`
     - `FORWARD`: `-i tun0 -o rv<ID>h -d <GUEST_IP>/32 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT`
     - `nat POSTROUTING`: `-s <GUEST_IP>/32 -o tun0 -j MASQUERADE`（将容器源 IP 伪装为 `tun0` 本端 IP，确保回包匹配 `tun0` 并在宿主内核还原给容器，同时防止 `tun0` 原路回环：因为 FlClash 自身处于 VPN 排除列表，其发向上游服务器的外网 socket 仍走 `wlan0`/`eth0`）。
- **已知边界与限制（必须在 UI 与文档中明示）**：
  - 宿主 VPN 客户端若开启了“分应用白名单模式（仅代理指定宿主 App）”，Android `VpnService` 仅按本机 UID 路由，不会改变 `tun0` 本身存在性但部分客户端底层策略/Fake-IP 规则可能对 `tun0` 直接收到的第三方 DNS（如容器默认 DHCP 下发的 `1.1.1.1`/`8.8.8.8`）处理方式不同。
  - 若宿主 VPN 启用了 `fake-ip` 模式且仅对 `tun0` 的 53 端口做 DNS 劫持，容器侧的 Private DNS（DoT 853 端口，实机可见 Guest `UsePrivateDns: true`）可能会与 Fake-IP 冲突；建议在此模式下同步下发明确提示或建议容器关闭严格 Private DNS / 配合模式 4。
  - 需配置 `vpnFallback` 子开关：`fallback_physical`（VPN 关闭后自动切回物理网卡不断网）或 `fail_closed`（VPN 关闭后阻止公网转发，仅保留局域网/网关连通，防代理断开后直连泄露）。

### 模式 4：`host_proxy`（宿主代理端口协同模式 — 本次实测已验证可用基础）
针对宿主代理软件已开启“允许局域网代理（`allow-lan: true`）”（如本次 FlClash 开放 `[::]:7890`）：
- **工作流**：
  1. 实例内网关即 `$GATEWAY`（如 `172.30.10.1`），宿主监听端口由用户在 APK 内填写或自动探测常见端口（如 `7890` / `9981` / `10808`）。
  2. Host 放行从 `rv<ID>h`（源 `<GUEST_IP>/32`）到本机端口 `<PORT>` 的 `INPUT` 流量（或校验 Android `bw_INPUT`/`fw_INPUT` 不拦截）。
  3. 容器就绪后通过可控宿主工具下发/同步 Guest `settings put global http_proxy <GATEWAY>:<PORT>`；切回其他模式或停机清理时按需清除（`settings put global http_proxy :0` / `delete global http_proxy`），避免切换网络后容器一直带着失效的 `http_proxy` 导致全网断联！
- **定位**：这是对 Android 应用层（Google Play、YouTube、Chrome、绝大多数游戏 HTTP/HTTPS 请求）**兼容度最高、最稳定**的模式；但对完全绕过系统代理且目的 IP 被墙的纯 UDP/裸 TCP 流量无效，可与模式 3 或提示信息清晰区分。

## 六、Viewer APK 与 BufferBroker 控制面设计

### 6.1 Broker 状态与接口扩展
- **`/state` 扩展字段**（供管理页展示实时诊断）：
  - `network.mode`：`follow_host_uplink` / `fixed_uplink` / `host_vpn_tun` / `host_proxy`
  - `network.effectiveUplink`：当前实际绑定出口（如 `wlan0`、`eth0`、`tun0`、`none`）
  - `network.hostActivePhysical`：宿主当前探测到的物理活动网卡及可用候选列表
  - `network.hostVpnActive`：宿主当前是否存在活跃 `tun0`
  - `network.proxyPort` & `network.proxyReachable`（可选连通性自检）
- **新增接口**：
  - `POST /action?id=<ID>&type=network&mode=<...>&iface=<...>&port=<...>&vpnFallback=<...>`
    - 允许**停机保存**及**运行中安全热切换**（通过 `network.sh reconcile` 持有 `network.lock` 原子更新）。
  - 可选增加全局宿主网络状态刷新：由 Broker 监听宿主 `ConnectivityManager.NetworkCallback`（主网络切换、VPN 接入/断开），去抖 `1s` 后对开启了动态跟踪的运行中实例触发 `reconcile`。

### 6.2 Viewer APK UI 交互设计
在实例卡片操作区（与“分辨率 / 内存 / ROOT”并列，或放入“网络出口”弹窗）增加 **“网络出口”** 入口：
1. **卡片状态摘要**：直接显示一行小字，如 `出口：自动 (wlan0)`、`出口：VPN (tun0)` 或 `出口：宿主代理 (:7890)`，异常时提示（如 `宿主 VPN 未开启`）。
2. **配置弹窗内容**：
   - 单选出口模式：**自动跟随宿主网络（推荐）** / **锁定指定网卡（下拉列出现有物理接口）** / **跟随宿主 VPN（`tun0` 透明转发）** / **宿主局域网代理（端口可填，附一键检测连通性按钮）**；
   - 若选 `host_vpn_tun`：显示“宿主 VPN 断开时处理”开关（自动切回直连 vs 断开公网防止直连）；
   - 一键“测试当前出口”按钮：直接复用宿主/容器探测返回 `物理网出口` 与 `Google 204` 状态，避免盲调。
   - 双语字符串同步维护在 `app/viewer/i18n/translations.json` 并通过 `tests/i18n_catalog.py` 校验。

## 七、分阶段实施与验收计划（评审通过后执行）

1. **Phase 1：L1 动态物理探测与运行期热切换（高确定性、无侵入）**
   - 实现 `iris_probe_active_uplink` 与 `network.sh reconcile`；在树莓派上实测启动前后、切 Wi-Fi / 插拔 `eth0` 的自动切换与精确回收。
2. **Phase 2：验证 `host_vpn_tun` 内核实机兼容性**
   - 先在树莓派上以单实例 `1010` 实测 `iif rv1010h lookup tun0` + `MASQUERADE -o tun0` + Private DNS / Fake-IP 下 Google Play、YouTube、COC 及无 `INTERNET` 权限隔离用例（`network_denial.py`），确认无 Netd `fwmark`/conntrack 阻断后再合入脚本与 UI。
3. **Phase 3：Broker Callback + Viewer APK“网络出口”UI**
   - 接入 `/state` 与 `/action` 扩展、Android `NetworkCallback` 监听、Viewer 双语弹窗及配置持久化。
4. **Phase 4：全套自动化回归与多场景断网/切换压力验收**
   - 新增自动化测试覆盖 `follow_host_uplink`、`host_proxy` 启停清理（避免残留失效 `http_proxy`）、`tun0` 启停及 `recovery_regression.py` 账本/BPF 完整校验。

## 八、落地实现与真机边界记录（`0.2.1 / 0.2.1-e29`）

本方案已在 `0.2.1`（`versionCode=122`、`engine=0.2.1-e29`）完成核心落地并与原设计保持一致的策略模型，同时结合树莓派 4 实机表现作了如下工程调整与边界固化：

1. **双通道轻量热切换触发（替代 `ConnectivityManager.NetworkCallback`）**：
   - `BufferBroker` 未采用宿主 Android Java 层 `NetworkCallback`（避免依赖高权限进程持有额外系统广播/回调引用及跨进程上下文风险），改为在 `monitor()` 中每 **3 秒** 通过独立单线程 `networkReconciler` 执行 `network.sh host-probe`，并在物理接口或 VPN 状态变化、以及新实例刚完成桌面就绪（`sys.boot_completed=1`）时异步触发 `reconcile`。
   - `engine/runtime/watchdog.sh` 同时在守护循环中每 **5 秒** 调用一次 `network.sh reconcile "$ID" "$NET_REQ_SESSION" "$LOG"`，形成控制面与守护面双保险；无变化时走配置/路由幂等快路径零修改退出。
2. **宿主 `tun0` 销毁导致 `rt_tables` 映射丢失与孤儿数字表规则清理（实机排查修复）**：
   - 树莓派实机压测 FlClash 关闭/断开 VPN 时发现：Netd 销毁 `tun0` 后会同步移除 `/data/misc/net/rt_tables` 中 `tun0` 的名称映射，导致宿主内尚未删除的 `12009: from all iif rv<ID>h lookup tun0` 在 `ip rule show` 中退化为纯数字表名（如 `lookup 1017`）。原按名称 `lookup tun0` 精确匹配删除会失效，从而在切换至 `fail_closed`（期望无 `12009` 规则）或 `ctl.sh stop` 时残留孤儿策略路由并引发 `cleanup incomplete`。
   - **修复**：在 `engine/runtime/network.sh` 新增 `prune_orphan_out_rules`，按规则优先级 `$PREF_OUT:` / `$PREF_OUT_FALLBACK:` 与入接口 `iif $IFACE` 从 `ip rule show` 提取实际 `lookup <table>`（兼容名称和数字表 ID），在 `reconcile` 与 `cleanup_owned` 时清扫所有不在 `TARGET_RULES` 中的残留规则；并在 `_in_sync` 中增加 `out_rule` 实际行数与预期数量对比校验。
3. **无网先启动与快速离线探测**：
